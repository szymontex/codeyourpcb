Proof: `cypcb check examples/drc-test.cypcb` reports `R1 silkscreen over R2.1: 0.12mm actual, 0.13mm required`; blink stays clean. `rotate_point`, which had been copy-pasted into two rules, now lives once in `rules/mod.rs`.
- **The new rule found a defect in the geometry it depends on.** `segment_distance`'s degenerate-first-segment branch computed `t = f/e` where the maths gives `-f/e`, which walks the closest point to the wrong end of the segment. The general branch computes `(b*s - f)/e` - the same thing with the right sign - so the two disagreed. Nothing had exercised it: its only caller, `point_to_segment_distance`, carried `#[allow(dead_code)]`. Silkscreen violations were silently under-reported until it was fixed, and a regression test now pins the perpendicular case, the past-the-end case and argument symmetry.
- DONE: **a clearance the design states is enforced.** `net HV [clearance 0.6mm]` parsed, reached the board model with M1, and the checker went on applying the fab preset to every pair - so a rule the designer wrote was silently replaced by a weaker one. The requirement for a pair is now the strictest thing either side asked for, never below the fab floor. Two things had to change with it: the broad phase expanded its query by the preset, so a pair needing more space was filtered out before anyone could ask what it required; and the net set was read from entities carrying a `NetId`, which misses a board with no traces yet, so it comes from the net registry now. Proven on one board, twice: clean under the preset, and `R1 ↔ R2: 0.30mm actual, 0.60mm required` once HV states 0.6mm.
- DONE: **clearance is a copper rule, and it was being measured against part bodies.** A component sits in the spatial index as its footprint's **courtyard** - the assembly keepout over the whole body - and `ClearanceRule` measured traces against that box. So a trace running through the 0.4mm gap between a 0402's two pads, which every real board does, was reported as a dead short at 0.00mm. The narrow phase now resolves a component to its pad copper, the way it already resolved a trace to its segments, and honours each pad's own layers: a bottom-layer trace cannot short a pad that only exists on top. Two failures came out of the same investigation. `CourtyardClearanceRule` - the rule that is *supposed* to own body collisions - filtered the spatial index for `layer_mask == 0`, and no index builder in the crate sets that (components are indexed `0xFFFFFFFF`), so it silently reported zero on every board ever checked; it reads the components directly now. And `parse_kicad_pcb` never called `set_footprints`, so on an imported board the world held no footprints at all and every rule that needs pad or silk geometry quietly degraded. Measured with `drc_report`, before / after: stm32_breakout **173 -> 124 introduced** (clearance 152 -> 103), multi_ic **122 -> 42** (clearance 108 -> 28), led_blink 0 -> 0. The pre-routing baselines rose the other way as the blind rules woke up - multi_ic 5 -> 60, of which 23 courtyard-clearance, 20 solder-mask-bridge and 19 silk-clearance were always true of that fixture and never once reported. Workspace: 52 targets, 1315 passed, 0 failed.
- DONE: **the repair pass was costing 3.4x the routing time and returning nothing, so it is off by default now.** `repair_routes` narrates every decision through `tracing`, and no test had ever turned a subscriber on - so the pass ran blind for as long as it has existed. `tests/repair_report.rs` (`--ignored`) turns it on: on multi_ic every attempt measures **worse** than the board it started from (129, 117, 126, 112 against a baseline of 109) and zero are accepted. Timed on the same fixture, same output both ways: **259.5s with repair, 74.7s without, 1027 routes and 109 violations either way.** Four full re-routes of the board for nothing. `repair_passes` now defaults to 0; the machinery stays, documented with these numbers, and what it needs before it goes back in the default path is an instrument that works in nanometres rather than whole cells - blocking a 0.254mm cell to fix a 0.05mm overlap moves the route further than the problem does.
- DONE: **repair was also judging itself on work it cannot do.** `measure` returned `report.violations.len()` - every violation on the board, including silkscreen over a pad, a part off the board edge and a pin nobody wired, none of which a reroute can touch. It counts only the positional kinds it already filtered for its blocker list. On multi_ic that is 45 rather than 109. The decisions do not change on this fixture, since the unactionable part is constant; on a board where it is not, a pass could have been accepted for improving something it never touched.
- NEXT-ACTION: the largest shape is trace-against-via, 66 of stm32_breakout's 103, and every cell-level instrument tried against it has made the board worse (via-ring ownership, and now the repair pass, both measured). - DONE: **the same-net exemption is per pad now, and it was blind in a way no benchmark would have shown.** It exempted a pair as soon as the component carried the trace's net anywhere, so a trace on `GND` crossing the `VCC` pad of a part with one GND pin was silently legal - a dead short the checker was built to catch. Proven both ways on the same fixture: the new test fails on the previous commit (`git stash push crates/cypcb-drc/src/rules/clearance.rs` -> `a_net_a_part_carries_does_not_exempt_that_part_s_other_pads ... - DONE: **measured what the per-pad exemption costs, and it found a real short on the smallest board.** Introduced violations went stm32_breakout **124 -> 174**, multi_ic **42 -> 79**, led_blink **0 -> 1**. Every one of those was already on the board; the checker had been excusing them. led_blink's is worth naming because it is one line: `C1 ↔ trace 'GND': 0.00mm actual` - and the fixture's own netlist puts C1 pad 1 on `SW_OUT`, pad 2 on `GND`, so a GND trace is lying across the switch output. That board does not blink.
- **The mechanism is found and it is not the grid.** `pad_to_zone` builds a disc around every pad of the net being routed - pad radius plus a hard-coded 3 cells, about 0.76mm at this resolution - and inside that disc `find_path_congestion_augmented` accepts a cell whether or not it is an obstacle. The escape hatch exists so a route can reach its own pad through the pad's own keepout. It does not distinguish the target pad from the part's other pads, so a GND route arriving at C1 pad 2 may drive straight over C1 pad 1 on the way in.
- **Two ratchets moved, both upward, both with the reason written at the assertion.** `smoother_integration_led_blink` from `== 0` to `<= 1`, and `benchmark_regression` from `drc_violations == 0` to `<= 1` with composite from 100.0 to 1100.0 (the composite charges 1000 per violation, so 42.6 of quality plus one short). Raising a ratchet is normally forbidden and this is the exception that proves it: the board is unchanged, the checker stopped being blind. Both comments say to put them back the moment the router stops driving through sibling pads.
- NEXT-ACTION: **close the pad-zone escape hatch.** A route may enter its own pad's keepout; it may not enter a foreign pad's. The data to tell them apart does not exist yet - `populate_pads` marks pad cells with `CELL_PAD` and no owner - so the fix is to give pad cells their net, matching `PadDef::number` to `PinConnection::pin` exactly as `cypcb-drc` now does, and then to accept a cell in a pad zone only when it is free or owned by the net being routed. Measure completeness as well as violations: this is a block, and every block tried so far has cost routes.
- DONE: **components say which face they are on.** A `Side` component with the three questions a face answers - which copper its SMD pads take, which silkscreen it prints to, and its layer-mask bit. The KiCad importer reads `(layer "B.Cu")` from a footprint, which is the only place in the codebase where the side is data rather than inference; sync derives it from the footprint's copper and stores the answer so every rule reads the same one. The silkscreen rule takes it and falls back to the old guess only when nothing states it. Proven on a two-footprint board where one is `F.Cu` and one `B.Cu`: `[("R1", Top), ("R2", Bottom)]`.

- **Failed experiment, tried twice, do not try a third time:** hard-blocking any cell within `clearance_cells` of foreign copper during path expansion. The geometry it targets is real - routes are marked cell by cell while a trace is twice a cell wide, so two nets in neighbouring cells overlap - but blocking is the wrong instrument. First attempt: 3 -> 4 violations, 22 -> 20 routes, composite 3542.6 -> 4043.6. Second attempt, after the congestion fixes made PathFinder converge properly: identical outcome, 4 violations and 19 routes. A hard block forbids legal geometry too (a trace may run at exactly the minimum clearance), so it costs routes without buying correctness. If this is attacked again it needs a **soft cost** in the neighbour cost function, or a post-route repair pass driven by actual DRC output - not a veto during expansion.
- DONE: **the router obeys a width the design states.** `net VCC [width 0.4mm]` was parsed, carried onto the board model by M1, and then ignored: `paths_to_output` took the width from `rules.constraints_for_net()`, and `PresetRuleSet` returns the same constraints whatever net it is asked about, so a designer's explicit instruction lost to the fab default on every trace. The stated width now wins, floored at the preset minimum - a design cannot ask for copper thinner than the board house will etch. Proven on a two-net board: VCC comes out at 0.4mm on every segment and the net that says nothing keeps the 0.127mm preset. The benchmark fixtures are KiCad imports and declare nothing, so 0/167/110 is unchanged.
- **That NEXT-ACTION was stale, and the check that would have caught it was one command.** The three violations on led_blink are gone - `drc_report` now prints `led_blink.kicad_pcb - Complete, 23 routes, 0 violations`, and `smoother_integration_led_blink` passes its `drc_violations == 0` assertion. - DONE: **the benchmark DRC numbers now say who caused them.** The fixtures are KiCad boards with parts already placed, so a violation in the routed board might be one the router made or one the import brought with it, and nothing distinguished the two. `drc_report` runs DRC twice - once on the fixture as imported, once after routing - and lists only what appears in the second run. Measured: led_blink 0 before / 0 after, stm32_breakout **3 before / 176 after / 173 introduced**, multi_ic **5 before / 127 after / 122 introduced**. The router is responsible for essentially all of them; blaming the fixtures would have been comfortable and wrong.
- NEXT-ACTION: **the dominant cause is a DRC defect, not a router defect.** Of 262 introduced clearance violations, 219 are at exactly 0.00mm and 116 are of the shape `component ↔ trace`. `ClearanceRule` measures a component as its spatial-index envelope, which is the footprint's **courtyard** - the part body - while the router marks only pad copper. A trace running under a 0402's body between its own pads is normal, legal manufacturing, and the checker calls it a short. Refine the narrow phase to actual pads, the way it already refines traces to segments, and add a separate courtyard-overlap rule so placement collisions (`J3 ↔ R3` at 0.00mm, present before routing) keep being reported instead of quietly disappearing.
- DONE: **a probe that says which half of the router to blame.** `tests/grid_vs_checker.rs` (`--ignored`) takes every clearance violation the router introduces, maps its coordinate onto the grid the router used, and reports what that cell was marked as - a route through a cell marked `CELL_PAD` means the search ignores its own obstacles, a violation on a free cell means the marking never happened. Cross-tabbed against the shape of the pair, stm32_breakout's 103: **trace-via 66 (64 of them on free cells)**, trace-trace 33 (18 on pad cells), via-via 3, part-via 1. multi_ic's 28: trace-trace 23 (20 on pad cells), trace-via 3, part 2. Grids are 296x256 at 0.254mm and 197x158 at 0.508mm per cell.
- **Failed experiment, measured, do not repeat: hard-owning the via ring in the grid.** The finding above has an obvious reading - a via's copper is never written into the grid at all, only into the congestion map, where it is a price a later net can pay rather than a fact it must respect. Marking the ring as the net's own copper (`mark_route` over `via_footprint_cells`) made both boards worse: stm32_breakout **124 -> 154** introduced (clearance 103 -> 125, hole-to-hole 3 -> 9, routes 858 -> 965), multi_ic **42 -> 55** (clearance 28 -> 38). Reverted, and the revert re-measured back to 124 / 42 exactly. This is the third time a hard block has cost more than it bought. The reason is arithmetic: the via keepout is `drill/2 + annular + clearance + width/2` = 0.15 + 0.127 + 0.127 + 0.0635 = 0.4675mm, which at 0.254mm per cell rounds up to a 2-cell disc - 0.508mm, nearly double the ring's actual 0.277mm of copper. At this resolution the grid cannot express via clearance without over-blocking. The honest routes are a finer grid near vias, or a post-route repair driven by real DRC output.
- **The repair pass currently buys nothing, and the tracker said otherwise.** `route_board` runs `strategy.route` and then `repair_routes`; the benchmark diagnostics called `strategy.route` directly, so they measured a router the product never ships alone. Pointed at `route_board` they report **exactly the same numbers** - 858 routes / 124 introduced and 1027 / 42, identical to the un-repaired path on all three fixtures. Repair therefore accepts no attempt on any of them today. The 176 -> 167 and 127 -> 110 recorded below were measured before the clearance rule was fixed, and no longer describe this code.

### V5 - Features from the roadmap
- DONE: nothing this cycle.
- DONE: **a copper pour can say what it is poured to.** The grammar has read `net` on a zone since the beginning, the parser filled `ZoneDef.net`, and sync ended at `let _ = net;` under a comment saying it would matter one day. `Zone` carries a `NetId` now, and the first thing that uses it is the ratsnest: a pad of that net sitting inside a pour on a layer the pour reaches is already connected by the plane, so the router is not asked to reach it. Proven both ways in one test - the same two-resistor board yields a GND net to route without the plane and none with it, while the signal between them still has to be routed.
- DONE: **modules can be instantiated, which is what makes them worth having.** `module Divider { ... }` parsed and defined a block nothing could reach - there was no instantiation syntax at all. `use Divider as DIV1 { IN = VIN, OUT = SENSE_A }` exists now, through the whole stack: a grammar rule and a regenerated `parser.c`, `ModuleInstance`/`PortConnection` in the AST, a converter in the parser, and expansion in sync. An instance copies the module's components under its own name, so two dividers are `DIV1_RTOP` and `DIV2_RTOP` rather than two `RTOP`s; an internal net is local the same way (`DIV1_MID`), while a net named by one of the module's pins becomes the design's net, which is the entire point of a pin. Expansion happens before every other pass, so nothing downstream needs to know modules exist. Two errors were added rather than left implicit: instantiating an undefined module, and leaving a declared pin unwired - which would otherwise silently become a local net and look connected. Proven end to end through the CLI: two instances of one divider yield four components, and the checker sees them as four.
- DONE: **an instance says where it goes.** `use Divider as DIV1 at 10mm, 5mm rotate 90` - without it every instance of a module landed on the last, and the two-divider board reported 8 violations that all said "these parts are in the same spot". A module places its parts in its own coordinates; the instance decides where those land. A turned instance turns its parts about that origin and adds its angle to each, so a rotated block behaves like the same block. Verified on the same board twice: `DIV1_RTOP` at (15mm, 10mm, 0deg) and `DIV2_RTOP` at (20mm, 10mm, 90deg) from one module whose RTOP sits at 5mm, 5mm - and `cypcb check` goes from 8 violations to `passed DRC`.
- DONE: **modules nest.** A module can be built from other modules, and expansion recurses: names compose (`BANK_LEFT_R1`), placements compose through both frames, and a port two levels down still reaches the design's own net - `SUPPLY = VIN` on the outer instance is what the inner `IN = SUPPLY` resolves to. Verified on a `Pair` of two `Divider`s placed inside one `BANK` at 20mm: the parts land at 22mm and 32mm, and `BANK_LEFT_IN` does **not** exist, because a pin wired through must not also become a local net. A module that instantiates itself, directly or through another, is reported as `module instantiates itself: A -> B -> A` rather than expanding for ever; no depth limit is needed, since a chain without repeats cannot outlast the file's module count. The grammar had to admit `use` inside a `module` body, which it did not.
- DONE: **`assert` is checked.** The grammar, the AST and the parser have carried assertions for a long time and nothing read them. They ride onto the board model like net constraints do, and `AssertionRule` evaluates them with the rest of DRC, so `cypcb check` reports them. `assert board.width <= 100mm` on a 120mm board says so with the number; `board.layers >= 2` on a 2-layer board is silent. Operands are typed - a length is refused a comparison with a resistance rather than being coerced into one. **An assertion the checker cannot evaluate is reported, not skipped**: `R1.value` comes back as "not something the checker can read yet", because a statement that quietly does nothing leaves the board looking checked, which is worse than one that fails. Known today: `board.width`, `board.height`, `board.layers`, and any literal.
- Also: violation messages no longer invent `entity #0:` for something the world cannot name. An assertion is about the board, not a part, and its message already reads as a sentence. Named entities are still labelled - `R1 ↔ R2: Clearance violation` is unchanged.
- DONE: **a component's value can be a quantity, and an assertion can read it.** The decision this needed had already been made by the language: `value_property` accepts `value 10kohm`, and the parser was flattening it - "convert the raw text to a StringLit so the component value field remains compatible". The type is kept now, alongside the string, and rides onto the board as a `TypedValue` component. `assert R1.value >= 47kohm` on a 10k part reports `but the board has 10000ohm`. A part written `value "10k"` is refused with the fix in the message: *write `value 10kohm` rather than `value "10k"`, or the checker has only a label to go on* - because "10k" is ten kilohms only if you already know the part is a resistor, and the checker should not be the one guessing.
- DONE: **assertions read nets.** `VBUS.current`, `VBUS.width` and `VBUS.clearance` resolve to what the net's own block states, which the board model has carried since M1. The field decides what kind of name it is - a part has a `value`, a net has those three - and `board` is neither, which is a collision the first attempt walked straight into: `board.width` matched the net branch and made a working assertion fail. A net that states nothing is not treated as satisfying everything; it is reported with the block to write.
- **Writing the test found a hole in the grammar.** `physical_unit` listed `uA` under a comment claiming `mA` and `A` were "already handled by current_unit". They were not listed, so `current 2A` parsed inside a net block while `assert VBUS.current >= 1A` was a syntax error. Both are units now. Proven end to end: `VBUS.current >= 1A` is silent on a 2A net, `VBUS.width >= 1mm` reports `but the board has 0.800mm`.

Only reusable definitions cross a file boundary: modules, footprints and interfaces. A board, a component or a net belongs to the design that wrote it, and letting those through would make `import` textual inclusion under another name. `import "x"` takes everything reusable, `import A, B from "x"` takes what it names and reports what is not there. Libraries can be built from libraries, and a file that imports itself is reported with the chain rather than followed. Wired into `check`, `score` and `route`, with import errors printed and the rest of the design still checked. Proven end to end: a `Divider` imported from `lib/blocks.cypcb` and instantiated twice passes DRC, and renaming it to one the library lacks reports `'lib/blocks.cypcb' does not define 'Regulator'`.
