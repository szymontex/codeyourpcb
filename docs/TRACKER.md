- DONE: **`cypcb export` runs the checker before it writes.** `check` and `export` were two commands with nothing joining them, so a shorted board went to a fabricator without a word. Export now measures the board against the same preset the checker uses, by the same lookup, and says what it is shipping: `Warning: exporting a board with 7 DRC violation(s). Run cypcb check <file> to read them.` The two agree - `cypcb check` on that file reports 7 - and a board that passes DRC exports with no such line. It does not refuse: whether to make a board with known faults is the designer's call and a fabricator makes whatever the files say. Refusing without a `--force` flag is a product decision and is left to the owner.
- DONE: **`ExportResult::warnings` was declared and never filled, promising warnings that never came.** It says two things now, both chosen because the files are written either way and nothing else stops them: a board with no traces is an unrouted design sent to be made, and an `Edge_Cuts` layer with no geometry is a board with no cut path. The first fires on `examples/blink.cypcb` - `Warning: the board has no traces: this exports an unrouted design` - and goes silent on the same board after `cypcb route --in-house`. The CLI prints them under the summary. An earlier version also warned about empty silkscreen and paste layers and was narrowed: a board with parts on one side has an empty legend on the other, and warning about the ordinary buries the one that matters.
- DONE: **the export job is checked as a set, not only file by file.** Every one of the thirteen files had its own test - copper against the routed board, mask against the copper, drill against the vias - and nothing checked that they all arrive. A job that silently writes twelve of thirteen sends a board house an order with a layer missing, and the first person to notice is the one holding the boards. The new test compares what `run_export` wrote against what the preset's own flags asked for, requires the drill and the assembly files an assembly preset implies, and confirms every file it claims to have written is on disk with something in it - an empty layer reads to a fabricator as a blank one. Mutation-checked by gating the bottom silkscreen off, which reports exactly `["delivery-B_SilkS.gbr"]`.
- DONE: **`parse-kicad`'s numbers are checked against the file they describe.** Components, segments, vias and nets are counted from the raw S-expression with a depth-aware scan that shares no code with the parser under test - a count taken with the same reader would agree with it whatever both did. All three benchmark fixtures match, and the one difference is pinned with its reason: KiCad declares `(net 0 "")` for copper belonging to nothing, so the reported net count is one below the file's declarations. A reader counting by hand finds that gap and has no way to tell which side is wrong. Mutation-checked by undercounting components by one, which turns it red. **That closes the CLI: all six commands now have a test that reads their output against the thing it claims to describe.**
- DONE: **every span in the AST is checked against the text it names.** Spans are what an editor underlines and what `cypcb check` points at, and a span off by a token underlines the wrong word while the parse succeeds, the model is right and nothing else notices. The new test walks the parsed AST as JSON rather than by construct, so anything added to the grammar is covered the day it appears in an example - `examples/blink.cypcb` and `examples/v2-modules.cypcb`, which between them use the whole language. Mutation-checked: shifting every span one byte left turns both red. The only mismatch it found is not one - a string literal's span covers its quotes while its value is the text between them, which is what an editor should underline.

- DONE: **diffed the two lists, and the file was not the one lying.** The 5-against-6 gap is two separate facts. One is cosmetic: the same violation reads `trace 'VCC' ↔ via 'GND'` before and `via 'GND' ↔ trace 'VCC'` after, because the pair is ordered by entity index and indices differ between a routed board and the same board parsed back. Operands are typed - a length is refused a comparison with a resistance rather than being coerced into one. **An assertion the checker cannot evaluate is reported, not skipped**: `R1.value` comes back as "not something the checker can read yet", because a statement that quietly does nothing leaves the board looking checked, which is worse than one that fails. Known today: `board.width`, `board.height`, `board.layers`, and any literal.
- Also: violation messages no longer invent `entity #0:` for something the world cannot name. An assertion is about the board, not a part, and its message already reads as a sentence. Named entities are still labelled - `R1 ↔ R2: Clearance violation` is unchanged.
- DONE: **a component's value can be a quantity, and an assertion can read it.** The decision this needed had already been made by the language: `value_property` accepts `value 10kohm`, and the parser was flattening it - "convert the raw text to a StringLit so the component value field remains compatible". A part written `value "10k"` is refused with the fix in the message: *write `value 10kohm` rather than `value "10k"`, or the checker has only a label to go on* - because "10k" is ten kilohms only if you already know the part is a resistor, and the checker should not be the one guessing.
- DONE: **assertions read nets.** `VBUS.current`, `VBUS.width` and `VBUS.clearance` resolve to what the net's own block states, which the board model has carried since M1. - **Third failed experiment:** reserving the full trace footprint at marking time (every cell within `trace_width/2 + clearance/2` of a path node, via the occupancy mechanism rather than a veto). led_blink went 3 -> 4 violations, 22 -> 20 routes. Same outcome as both veto attempts. The reservation is right in principle but it fights the A* cost model, which still plans on centre lines; whoever picks this up needs to change both together, or nothing.
- DONE: classified the remaining violations and followed the biggest group. On stm32_breakout: 114 trace-trace, 114 trace-via, 19 pad-trace, 35 via-via - **over half involve a via**, and 243 of 285 sit at exactly 0.00mm. The grid marked a via as a single cell while its ring is 0.554mm across, about nine cells, so other nets routed straight through it. Feeding the via's real footprint to the **congestion map** - as cost, through occupancy - rather than blocking those cells:

| led_blink | 2 | **1** | 0 |
| stm32_breakout | 299 | **238** | 0 |

  **This is the answer to three failed experiments.** Blocking cells (the two vetoes and the trace-footprint reservation) always traded completeness for correctness; the hard-blocked version of this very change left stm32_breakout with 6 unrouted connections. The same geometry expressed as a price the router can negotiate keeps every board complete and still removes a fifth of the violations. Ratchets tightened to 1/238/240.
- **Fifth failed experiment:** pricing every trace's footprint in the congestion map, the way the via footprint works. led_blink 1 -> 2 violations, stm32_breakout 238 -> 342, multi_ic 240 -> 263. Congestion pricing needs the priced feature to be *sparse*: a few dozen vias give a sharp signal, while every path node claiming a disc floods the map and the signal stops discriminating. Reverted.
- DONE: **the routing grid is a track pitch now, not half a clearance.** Every experiment so far tried to patch around a grid whose neighbouring cells are closer than two traces may be. Measured across resolutions on stm32_breakout: 238 violations in 127.8s at clearance/2, 193 at clearance, 199 at 1.5x, and **124 in 9.7s at `min_trace_width + min_clearance`**. One cell per legal track position means adjacency is clearance-legal by construction.

- DONE: **led_blink routes with zero DRC violations.** Re-classifying showed trace-trace had become the biggest group (64 of 106 on stm32, 56 of 100 on multi_ic), still ~80% at exactly 0.00mm - which on a track-pitch grid can only be diagonal corner-cutting: two diagonals crossing between cells without ever sharing one. Reverted: it trades one board against the other, and the ratchet discipline exists so that trade is not rationalised into the codebase.
- **Six experiments in, the pattern is the finding.** Every geometry lever - vetoing cells near foreign copper (twice), reserving trace footprints, pricing trace footprints, owning via rings - improves one benchmark board and worsens the other by a similar amount. The grid-level fixes that *did* land (track pitch, corner-cut refusal, obstacle bloat, via pricing) all improved every board at once. That difference says the remaining ~200 violations are no longer a geometry problem but a **cost-model** one: which conflicts the router should accept where.
- **Seventh failed experiment, and the one that was meant to work: the post-route repair pass.** Route, run the real DRC, forbid exactly the cells it complained about, route again, keep the result only if the violation count drops and the board stays complete. Built it (`route_with_blockers` on the strategy, a `Blocker` carrying a point and a layer mask, an accumulate-and-retry loop). Then measured the same binary on the same input three times:

| run | stm32_breakout, 2 repair passes |
|---|---|
| 1 | 115 |
| 2 | 135 |
| 3 | 129 |

  Against a baseline of 137. multi_ic never improved in any run (64 every time) and led_blink was already at zero, so repair exits immediately there. Reverted. A pass that cannot reproduce its own number is not shippable, and shipping it off-by-default is how this project ended up with empty DRC checkers and a disabled A*.
- **The measurement left a sharper question than the feature did: the router is deterministic without extra obstacles and nondeterministic with them.** Three runs, fresh process each, plain routing: byte-identical, 858 routes / 53 vias / 1630.67mm / 137 violations. Add blocked cells and the same three runs diverge. `extract_ratsnest` sorts by net ID, `order_nets` is a stable sort over it, `nets_needing_reroute` and the congestion map iterate Vecs - the entropy is somewhere else and is worth finding, because a router that answers differently each run cannot be ratcheted at all.
- DONE: **found it, and it was never the router.** The router is reproducible: three processes × three sequential routings on a world already holding applied traces gave byte-identical signatures on led_blink and stm32_breakout. What was not reproducible was **the DRC report itself** - two processes, same board, 308 violations both times and **152 of the printed lines different**: pair orientation flipped, and the reported coordinate moved. Chain: `apply_routes` grouped segments in a `HashMap<(NetId, Layer), _>` and spawned from it, so entity IDs came out in hash order; the spatial index is built over those entities; the clearance rule takes `location` from whichever of the two features the outer loop happened to be holding. Fixed at all three levels - spawn sorted by (net, layer), the violation reported lowest-entity-first with its location at the midpoint between the two features, and `run_drc` sorting its output canonically. Verified: two fresh processes, **0 differing lines**, counts unchanged at 0/176/127. `Layer` gained `Ord` for the sort.

Counts unchanged (0/176/127), report still byte-identical across two processes.

- **The planned repair optimisation is dead, and the measurement is why.** The idea was that repair re-routes the whole board to move a handful of nets, so ripping up only the nets named in violations would turn 23s into about a second. Measured instead of assumed - comparing every net's routed geometry before and after a repair pass:

| fixture | nets | changed by repair | first pass | with repair |
|---|---|---|---|---|
| stm32_breakout | 34 | **34 (100%)** | 6.6s | 27.8s |
| multi_ic | 47 | **45 (96%)** | 24.3s | 74.8s |

  Nothing to save. PathFinder is a negotiated-congestion router: blocking a few cells perturbs the congestion map that every net is planned against, so the whole board re-plans whether or not that was asked for. An incremental repair would either produce a different answer from the one the gate measures, or not be incremental.
- **What the numbers do suggest**, recorded rather than built: repair is already "route the board several times under different constraints and keep the best", which is the shape `variant.rs` implements for a different purpose. If the 3x wall clock ever needs paying down, unifying the two is the lever - not per-net rip-up.
- DONE: **the resolution question is settled, and the answer is that the current default is right.** Measured with `tests/resolution_sweep.rs` (`--ignored`), routing each fixture at its adaptive default and at finer grids, violations introduced by the router and seconds:

| fixture | 0.508mm | 0.254mm | 0.127mm |
|---|---|---|---|

  Halving the cell roughly doubles both the violation count and the runtime on the dense boards. That is not a paradox: the default 0.254mm is exactly `min_trace_width + min_clearance`, the legal track pitch, so neighbouring cells are clearance-legal by construction and a finer grid puts two nets close enough to touch. A quarter of the pitch was tried and abandoned - stm32_breakout ran over nine minutes without finishing against 20.5s at the default, and was killed; the sweep now skips past a cell cap and says so rather than leaving a row quietly missing. Anyone proposing a finer grid for the remaining violations should read this table first.
- **`grid_resolution_nm` was not being honoured on large boards.** `resolve_adaptive_grid_resolution` doubles the pitch above 80mm, and it applied that to an explicit setting too, so a caller asking for 0.254mm on multi_ic silently got 0.508mm - which is how the first version of the table above compared the same grid against itself and reported identical numbers twice.
