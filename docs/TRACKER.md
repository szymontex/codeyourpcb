### V4 - Architecture and deduplication
- DONE: manufacturer rules had two copies that disagreed - the router routed JLCPCB to 0.127mm clearance while the checker demanded 0.15mm, so a correctly routed board failed its own DRC. `cypcb-drc` already depended on `cypcb-rules` without using it; the seven fab presets are now one line each on top of `DesignRules::from_constraints`, and `drc_presets_do_not_diverge_from_routing_constraints` walks every pair so they cannot drift again. Proof: `cargo test -p cypcb-drc` -> 113 + 31 + 23 passed, consumers green, gate clean.
- DONE: settled the question the second parser rests on. `cypcb-parser`'s manifest says tree-sitter is "not WASM compatible"; it is - `cargo build -p cypcb-parser --target wasm32-unknown-unknown` succeeds, and so does the whole render crate with `--features native`. `PcbEngine::load_source` now lives in the wasm-bindgen impl, so the browser can reach it. Measured cost, wasm-pack release: 702,357 bytes with the parser absent against 804,520 with it exported, about 100KB.
- **Why the JS parser could not just be deleted, found by trying.** It is not only a parser. `getFootprintPads()` consults `dynamicFootprintRegistry`, a map the viewer fills at runtime from EasyEDA fetches: a `.cypcb` file names a package like `LQFP-48` without describing its pads, and for anything outside the built-in library the geometry only exists because the JLCPCB insert flow went and got it. The Rust engine had no way to be told about such a footprint, so switching to `load_source` would have rendered every fetched part as an empty outline. Proven rather than assumed - the engine answers `unknown footprint: 'XKCD-2'` for a package nobody handed it.
- DONE: `PcbEngine::register_footprint` closes that gap, on both targets - `JsValue` for the browser, a JSON string natively so it is testable without a browser - and lands in the same `FootprintLibrary` the parser resolves against. Three tests: an unknown package is a hard parse error until the footprint is registered and then parses clean with both pads in the snapshot; a registration survives three re-parses, because the editor re-parses on every keystroke while the fetch happens once; malformed pads come back as an error rather than silence. Verified in the generated bindings too: `wasm-pack build --features native` exports it.
- **Measured, so the size question is settled:** the wasm module with the tree-sitter parser compiled in is **841,166 bytes against 702,332** without, +139KB for +20%. That buys deleting ~600 lines of hand-written regex parser that has no unit tests at all - no vitest file imports `parseSource`, its only coverage is the Playwright suite.
- DONE: `PcbEngine::register_3d_model`, the second runtime registry the viewer keeps. Same story as a fetched footprint - nothing in a `.cypcb` file says which 3D model a package uses, and the viewer learns it from a supplier. Plain strings, so one method serves both targets; exported in the generated bindings. Tested three ways: no model before registration, the right model after, and a package nobody registered does not borrow someone else's.
- **"Retire the JS parser in one step" was wrong, and reading the adapter is what showed it.** `parseSource` is not the only thing in the way. The JS snapshot is the viewer's *board model* - traces, vias, drag, undo all mutate it - and `get_snapshot()` merges WASM's violations with two checks that exist only in JavaScript, `checkSilkClearance` and `checkTraceCurrentViolations`. `MockPcbEngine` is a second full implementation of that model for when WASM fails to load. Deleting the parser without those is not a smaller change, it is a broken one.
- **One claim in the adapter was already stale.** It caches the JS snapshot because the engine's "would have empty traces since we only populated components/board" - true of `load_snapshot`, where JavaScript hands over components and nothing else, and not true of `load_source`. Verified: `uat-routing-locked.cypcb` through `load_source` yields a snapshot carrying its `trace VCC` block. A regression test now says so.
- DONE: **the IPC-2221 trace-width formula was in five places, not four, and they disagreed.** `cypcb-calc` had the real implementation and zero consumers; `cypcb-lsp/hover.rs`, `viewer/src/wasm.ts` and *two* inline copies in `viewer/src/interaction.ts` each did the arithmetic again. The language server took 1 oz copper as **1.37 mils** where every other copy uses **1.378**, so its hover quoted a width 0.58% off what the router draws - 0.3021mm against 0.3004mm at 1A. The language server now calls `cypcb-calc`, which un-orphans that crate; `PcbEngine::min_trace_width_for_current_ma` exposes the same one implementation to the browser; the three JavaScript copies are one exported helper, which dies with the parser swap. Five down to two, one per language, and a test pins the engine to the calculator rather than to a number.
- DONE: **M1 closed, and the check it was blocking ships.** `NetRegistry` now carries a design's per-net constraints - width, clearance, current - as a `Vec` indexed by `NetId`, so a lookup is one bounds-checked load rather than a hash of a net name, and a board that declares nothing costs one `None` per net. `sync_ast_to_world` fills it from the `net X { ... }` block, which the DSL has always parsed and the board model has always thrown away. `TraceCurrentRule` reads it: a net that says `current 3A` and is drawn 0.2mm wide now fails, with the layer taken into account because buried copper cannot shed heat. Proof end to end, parser through CLI: `net VCC [current 3A]` on `uat-routing-locked.cypcb` reports `trace 'VCC' is 0.200mm wide for 3.0A: IPC-2221 wants 1.367mm on an outer layer`.
- **Same defect as K012, in the half nobody had checked.** `apply_routes` learned to spawn `NetId` as its own component so DRC's same-net exemption could see it. Traces written in the DSL never did: `sync_ast_to_world` spawned `(trace, span)`. So a hand-written trace collided with the pad it connects to, and every message about it read `trace '?'`. The same file went from 3 violations to 1 - the two clearance findings were false and the remaining one is real.
- **The swap was attempted and reverted, and the reason is not what the tracker said.** Every viewer capability the engine lacked is now in the engine, so the code side went fine: the adapter parsed through `load_source`, `parseSource` and the JS-only checks and `MockPcbEngine` came out - 1615 lines down to 695 - and `tsc`, `eslint` and vitest 149/149 were all clean. The application then failed to load. **`wasm-pack build --features native` produces a module with 25 unresolved imports from `env`**, and Vite cannot resolve them: `Failed to resolve import "env" from "pkg/cypcb_render.js"`.
- **What those 25 symbols are settles the question.** Not libc - they are tree-sitter's own runtime plus our grammar: `ts_parser_new`, `ts_tree_root_node`, `ts_tree_cursor_goto_first_child`, `tree_sitter_cypcb` and 21 more.
- **Correction to the line above, which this tracker got wrong for one commit: the C *is* compiled, for the wrong architecture.** `target/wasm32-unknown-unknown/.../libtree-sitter.a` exists and its members are ELF machine 62 - x86-64. The container has `/usr/bin/gcc` and no clang, so `cc` was handed `TARGET=wasm32-unknown-unknown`, fell back to the host compiler and archived host objects. **The wasm linker skips wrong-architecture archive members in silence**, which is why `cargo build --target wasm32-unknown-unknown` reported success and why the earlier measurement in this file - "the parser does build for wasm32" - was true about the command and worthless about the artifact.
- DONE: **the build says so now instead of shipping it.** `cypcb-parser/build.rs` reads the object `cc` produced and refuses a wasm32 build whose first object does not start with `\0asm`, naming both ways out. Verified in both directions: `cargo build -p cypcb-parser` native still finishes, and the wasm32 build stops with `the C parser was compiled for the wrong architecture ... starts with [127, 69, 76, 70]`. The shipping build is untouched - `--features wasm` still produces 0 imports from `env`.

### V5 - Features from the roadmap
- DONE: nothing this cycle.
- DONE: **a copper pour can say what it is poured to.** The grammar has read `net` on a zone since the beginning, the parser filled `ZoneDef.net`, and sync ended at `let _ = net;` under a comment saying it would matter one day. `Zone` carries a `NetId` now, and the first thing that uses it is the ratsnest: a pad of that net sitting inside a pour on a layer the pour reaches is already connected by the plane, so the router is not asked to reach it. Proven both ways in one test - the same two-resistor board yields a GND net to route without the plane and none with it, while the signal between them still has to be routed.
- DONE: **modules can be instantiated, which is what makes them worth having.** `module Divider { ... }` parsed and defined a block nothing could reach - there was no instantiation syntax at all. `use Divider as DIV1 { IN = VIN, OUT = SENSE_A }` exists now, through the whole stack: a grammar rule and a regenerated `parser.c`, `ModuleInstance`/`PortConnection` in the AST, a converter in the parser, and expansion in sync. An instance copies the module's components under its own name, so two dividers are `DIV1_RTOP` and `DIV2_RTOP` rather than two `RTOP`s; an internal net is local the same way (`DIV1_MID`), while a net named by one of the module's pins becomes the design's net, which is the entire point of a pin. Expansion happens before every other pass, so nothing downstream needs to know modules exist. Two errors were added rather than left implicit: instantiating an undefined module, and leaving a declared pin unwired - which would otherwise silently become a local net and look connected. Proven end to end through the CLI: two instances of one divider yield four components, and the checker sees them as four.
- DONE: **an instance says where it goes.** `use Divider as DIV1 at 10mm, 5mm rotate 90` - without it every instance of a module landed on the last, and the two-divider board reported 8 violations that all said "these parts are in the same spot". A module places its parts in its own coordinates; the instance decides where those land. A turned instance turns its parts about that origin and adds its angle to each, so a rotated block behaves like the same block. Verified on the same board twice: `DIV1_RTOP` at (15mm, 10mm, 0deg) and `DIV2_RTOP` at (20mm, 10mm, 90deg) from one module whose RTOP sits at 5mm, 5mm - and `cypcb check` goes from 8 violations to `passed DRC`.
- DONE: **modules nest.** A module can be built from other modules, and expansion recurses: names compose (`BANK_LEFT_R1`), placements compose through both frames, and a port two levels down still reaches the design's own net - `SUPPLY = VIN` on the outer instance is what the inner `IN = SUPPLY` resolves to. Verified on a `Pair` of two `Divider`s placed inside one `BANK` at 20mm: the parts land at 22mm and 32mm, and `BANK_LEFT_IN` does **not** exist, because a pin wired through must not also become a local net. A module that instantiates itself, directly or through another, is reported as `module instantiates itself: A -> B -> A` rather than expanding for ever; no depth limit is needed, since a chain without repeats cannot outlast the file's module count. The grammar had to admit `use` inside a `module` body, which it did not.
- DONE: **`assert` is checked.** The grammar, the AST and the parser have carried assertions for a long time and nothing read them. They ride onto the board model like net constraints do, and `AssertionRule` evaluates them with the rest of DRC, so `cypcb check` reports them. `assert board.width <= 100mm` on a 120mm board says so with the number; `board.layers >= 2` on a 2-layer board is silent. Operands are typed - a length is refused a comparison with a resistance rather than being coerced into one. **An assertion the checker cannot evaluate is reported, not skipped**: `R1.value` comes back as "not something the checker can read yet", because a statement that quietly does nothing leaves the board looking checked, which is worse than one that fails. Known today: `board.width`, `board.height`, `board.layers`, and any literal.
- Also: violation messages no longer invent `entity #0:` for something the world cannot name. An assertion is about the board, not a part, and its message already reads as a sentence. Named entities are still labelled - `R1 ↔ R2: Clearance violation` is unchanged.
- DONE: **a component's value can be a quantity, and an assertion can read it.** The decision this needed had already been made by the language: `value_property` accepts `value 10kohm`, and the parser was flattening it - "convert the raw text to a StringLit so the component value field remains compatible". The type is kept now, alongside the string, and rides onto the board as a `TypedValue` component. `assert R1.value >= 47kohm` on a 10k part reports `but the board has 10000ohm`. A part written `value "10k"` is refused with the fix in the message: *write `value 10kohm` rather than `value "10k"`, or the checker has only a label to go on* - because "10k" is ten kilohms only if you already know the part is a resistor, and the checker should not be the one guessing.
- DONE: **assertions read nets.** `VBUS.current`, `VBUS.width` and `VBUS.clearance` resolve to what the net's own block states, which the board model has carried since M1. The field decides what kind of name it is - a part has a `value`, a net has those three - and `board` is neither, which is a collision the first attempt walked straight into: `board.width` matched the net branch and made a working assertion fail. A net that states nothing is not treated as satisfying everything; it is reported with the block to write.
- **Writing the test found a hole in the grammar.** `physical_unit` listed `uA` under a comment claiming `mA` and `A` were "already handled by current_unit". They were not listed, so `current 2A` parsed inside a net block while `assert VBUS.current >= 1A` was a syntax error. Both are units now. Proven end to end: `VBUS.current >= 1A` is silent on a 2A net, `VBUS.width >= 1mm` reports `but the board has 0.800mm`.
- NEXT-ACTION: `interface` and `import` are the last DSL v2 constructs that parse and do nothing. `import` is the more useful of the two - a module library is only worth writing if another file can use it - and it needs a decision about resolution: relative to the importing file, or to a project root.
